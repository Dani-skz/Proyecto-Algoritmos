1. Idea del proyecto

Aplicación de escritorio en C# con Windows Forms que presenta un test tipo quiz ambientado en un mundo medieval de fantasía. A partir de las respuestas del usuario, el sistema determina qué raza y qué clase sería, y le asigna un resultado combinado (por ejemplo: mayormente elfo y en segundo lugar orco → Elfo oscuro).

Cambio de dominio: la cátedra autorizó reemplazar el sistema de coworking por otro tipo de sistema, siempre que se cumplan los puntos de la consigna. Este documento muestra cómo se cubre cada uno.

Mecánica

  • El usuario ingresa su nombre y elige el modo de juego.
  • Cada pregunta tiene aproximadamente 6 respuestas posibles, presentadas como imágenes clickeables.
  • Cada respuesta suma una cantidad de puntos predefinida a una o más variables (razas o clases).
  • Al finalizar, se determinan la raza principal, la raza secundaria y la clase dominante, y se asigna el resultado final.
  • Se guardan en MySQL el nombre del jugador, el puntaje final de cada variable y el resultado asignado.
Pregunta: En una guerra, ¿rematarías a tu enemigo o perdonarías su vida? [imagen] Lo perdono → +puntos Humano [imagen] Lo remato con piedad → +puntos Elfo [imagen] Lo devoro → +puntos Orco [imagen] Le doy un martillazo en la cabeza → +puntos Enano ...

Modos de juego

Modo clásico

Las preguntas se presentan una tras otra, sin contexto adicional.

Modo narrativo

Antes de cada pregunta se muestra un fragmento de una historia que avanza con el test y busca influir en las respuestas del usuario.

2. Alcance

Incluido

  • Test en modo clásico y modo narrativo.
  • Preguntas de raza y de clase, con puntajes predefinidos.
  • Cálculo del resultado combinado (raza principal + secundaria).
  • Registro de jugadores y partidas en MySQL.
  • Historial de partidas con filtros.
  • Estadísticas de resultados.
  • Modificación de jugadores y anulación de partidas.
  • Interfaz con imágenes clickeables y pseudo-animación al hacer click.
  • Manejo de errores de MySQL y de la aplicación.
  • Respaldo automático del historial en JSON.

Fuera de alcance

  • Preguntas en la base de datos: son contenido fijo del juego, por lo que se definen en el código. La base guarda los resultados.
  • Editor de preguntas desde la interfaz.
  • Usuarios con contraseña o roles.
  • Modo multijugador.
  • Animaciones gráficas complejas (Windows Forms no es un motor de juegos).
Justificación del diseño: se trata de una demo académica. Mantener las preguntas en el código simplifica la arquitectura sin afectar los requisitos, ya que la persistencia se concentra en los resultados, que son los datos que efectivamente cambian.

4. Base de datos MySQL

La base almacena los resultados del test. Los puntajes se guardan como filas (una por variable) y no como columnas por raza, para evitar información duplicada y permitir vistas y funciones sobre ellos.

Modelo propuesto

TablaCampos principalesPropósito
variablesid_variable (PK), nombre, tipo ENUM('RAZA','CLASE')Catálogo de razas y clases evaluadas.
jugadoresid_jugador (PK), nombre (UNIQUE), fecha_altaPersonas que realizaron el test.
resultadosid_resultado (PK), id_raza_principal (FK), id_raza_secundaria (FK), nombre, descripcion · UNIQUE(principal, secundaria)Catálogo de combinaciones: Elfo + Orco → Elfo oscuro.
partidasid_partida (PK), id_jugador (FK), fecha, modo ENUM('CLASICO','NARRATIVO'), id_resultado (FK), id_clase (FK), estado ENUM('VALIDA','ANULADA')Cada vez que alguien completa el test.
partida_puntajesid_partida (FK), id_variable (FK), puntos · PK compuestaPuntaje final de cada variable en la partida.
auditoria_partidasid_auditoria (PK), id_partida, accion, fecha, detalleRegistro generado por el trigger.

Restricciones de integridad

  • Claves primarias y foráneas en todas las relaciones.
  • CHECK (puntos >= 0) en los puntajes.
  • CHECK (id_raza_principal <> id_raza_secundaria) en los resultados.
  • Nombre de jugador único y no vacío.
  • No se elimina información: las partidas se anulan (baja lógica).

Procedimientos almacenados

ProcedimientoOperaciónEquivalente en la consigna
sp_registrar_jugadorAlta del jugador, o reutiliza el existente si ya jugó antes. Devuelve su id.Alta de cliente
sp_modificar_jugadorCorrige el nombre de un jugador.Modificación
sp_registrar_partidaCrea la partida con su modo. Devuelve su id.Alta de reserva
sp_guardar_puntajeGuarda el puntaje final de una variable.Alta
sp_finalizar_partidaValida que estén todos los puntajes y asigna resultado y clase usando la función.Operación principal
sp_anular_partidaBaja lógica de una partida.Cancelación de reserva

Reglas de negocio con SIGNAL SQLSTATE '45000'

  • Nombre de jugador vacío o con menos de 2 caracteres.
  • Modificar un jugador con un nombre que ya usa otro.
  • Guardar un puntaje negativo o para una partida inexistente.
  • Finalizar una partida a la que le faltan puntajes.
  • Anular una partida que ya está anulada.

Vistas

vw_historial

Jugador, fecha, modo, resultado asignado, clase y estado de cada partida. Alimenta el historial y la exportación JSON.

vw_estadisticas_resultados

Cantidad y porcentaje de partidas válidas por resultado y por raza principal.

Función definida por el usuario

fn_resultado_combinado(id_partida): obtiene las dos razas con más puntos de la partida y devuelve el id del resultado correspondiente en la tabla resultados. El cálculo del resultado vive solo en la base; la aplicación no lo duplica.

Trigger

trg_auditoria_partidas: registra en auditoria_partidas cada partida finalizada y cada anulación, con fecha y detalle.

Antes de pasar a C#: probar en Workbench todos los procedimientos, las vistas, la función, las restricciones y el trigger, con datos iniciales de prueba. Guardar el script completo de creación de la base.

5. Programación Orientada a Objetos

Pregunta (abstracta) │ Texto, Respuestas : List<Respuesta> │ abstract void Aplicar(Respuesta r, Perfil p) ├── PreguntaRaza → suma los puntos a las variables de raza └── PreguntaClase → suma los puntos a las variables de clase Test (abstracta) │ Preguntas : List<Pregunta>, IndiceActual │ abstract string TextoPrevio(int indice) ├── TestClasico → "Pregunta 3 de 12" └── TestNarrativo → fragmento de la historia antes de cada pregunta «interfaz» IPuntuable │ void SumarA(Perfil perfil) └── Respuesta → Texto, Imagen, Puntos : Dictionary<string,int> Perfil → PuntosRaza, PuntosClase : Dictionary<string,int> Jugador → Id, Nombre Partida → Id, Jugador, Fecha, Modo, Resultado, Clase, Estado GestorQuiz → coordina la partida: arma el test, recibe respuestas, registra el resultado ConexionBD → conexión centralizada a MySQL ExportadorJson → respaldo automático del historial

Uso de cada concepto

  • Clases abstractas: Pregunta y Test definen lo común; cada derivada aporta comportamiento propio.
  • Polimorfismo: el test recorre una List<Pregunta> mezclada y llama a Aplicar() sin saber si es de raza o de clase. De la misma forma, el formulario llama a TextoPrevio() sin saber qué modo se eligió.
  • Interfaz: IPuntuable representa la capacidad de otorgar puntos a un perfil.
  • Colecciones genéricas: List<Pregunta>, List<Respuesta>, Dictionary<string,int> para los puntajes.
  • Responsabilidades: los formularios solo muestran y capturan datos; las reglas están en las clases del dominio y en GestorQuiz.
Cuidado con la clase gestora: GestorQuiz no debe concentrar interfaz, reglas y SQL. Cuando se vea DAO, el acceso a datos se traslada a JugadorDAO y PartidaDAO.

ComboBox: muestran descripciones (nombre del resultado o de la raza) y conservan internamente el id para operar con la base, mediante DisplayMember y ValueMember.

Respuestas como imágenes

Las respuestas se presentan con PictureBox en lugar de botones. Al hacer click, un Timer reduce la imagen unos píxeles y la restaura a los 100–150 ms, generando una pseudo-animación de "presionado". No se usa Thread.Sleep, ya que congela la interfaz.

Conexión

Formularios ↓ GestorQuiz / clases del dominio ↓ acceso a datos (luego JugadorDAO, PartidaDAO) ↓ ConexionBD ↓ MySQL

7. Manejo de errores

try { // registrar partida en MySQL } catch (MySqlException ex) { if (ex.SqlState == "45000") // regla de negocio: mostrar ex.Message al usuario else // error general de MySQL (conexión, integridad, etc.) } catch (Exception ex) { // error de la aplicación }

Registro de partida + respaldo JSON

Son dos operaciones independientes y se tratan por separado:

  • Falla MySQL: la partida no se guardó. Se informa el error y no se exporta.
  • MySQL guarda pero falla el JSON (archivo abierto, sin permisos): la partida quedó registrada. Se muestra un aviso: "Resultado guardado, pero no se pudo actualizar el respaldo".
No se utilizan bloques catch vacíos. Todo error se informa al usuario.

8. Requerimientos evolutivos

JSON: respaldo automático Durante la cursada

sp_finalizar_partida OK ↓ lectura de vw_historial → List<Partida> ↓ serialización a JSON ↓ historial_partidas.json (se reescribe completo)

Después de cada partida registrada correctamente, se exporta el historial completo leído desde la base. Al reescribir el archivo desde la vista, el JSON siempre coincide con MySQL, incluidas las anulaciones. La exportación está a cargo de ExportadorJson, no del formulario.

Finalidad: respaldo de los resultados y posibilidad de compartirlos fuera del sistema.

Acceso a datos / DAO Durante la cursada

Trasladar el código de MySQL desde GestorQuiz y los formularios a JugadorDAO y PartidaDAO.

Configuración externa Durante la cursada

Retirar los datos de conexión de ConexionBD y leerlos desde la configuración de la aplicación.

Estos puntos se implementarán una vez explicados en clase, según la regla de trabajo de la consigna.
